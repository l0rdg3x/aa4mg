Device-checked on 2026-10-17 with a build of beb933e (Nothing Phone 2, LineageOS 23.2, KernelSU-Next + Hybrid Mount): the installer accepted it and the module is active (its CHANGELOG is in /data/adb/modules/aa4mg); under /product the stub, privapp XML and overlay match the expected sha256 and the stub has no oat files; the overlay com.nikgapps.overlay.androidauto is enabled; Android Auto holds the SYSTEM_AUTOMOTIVE_PROJECTION role and is a system package. In the car the maintainer reported that everything works. No logcat check of the privapp permissions was done.
- README states that the fork is maintained mainly for personal use.
- Installer fixes (merge dd97612): phenotype.db and .pb copies, the overwrite prompt and data/ removed (closes the symlink risk of the root copies into app-owned paths); IFS restored after the summary; warning when the metamodule is disabled or marked for removal (reachable only with metamodules without metainstall.sh: KernelSU-Next refuses the install for the others, so it cannot be tested with Hybrid Mount). Device-checked on 2026-10-18 with the 0.7.0 build of dc8221c (zip sha256 2028bd74…af4c; the release zip differs only in CHANGELOG): the install log shows the 4 prompts without the phenotype.db prompt, "- linked /product" and no warning; after the reboot /data/adb/modules/aa4mg/product links to ./system/product, the module has no data directory, under /product the stub, privapp XML and overlay match the expected sha256 and the stub directory holds only its APK, the overlay is enabled, Android Auto holds the SYSTEM_AUTOMOTIVE_PROJECTION role and is a system package. In the car the maintainer reported on 2026-10-18 that Android Auto works with this build. phenotype.db and the .pb already copied by older versions stay in place: nothing removes them.
- Action button (action.sh, merge 8ff0e86): uninstalls the Android Auto updates after a Volume UP confirmation within 10 s, because uninstall.sh runs at the next boot before PackageManager starts (KernelSU-Next), where pm fails; uninstall.sh is kept. Simulation-tested (Volume UP after another event, no updates, pm failure, Android Auto not a system app, Volume DOWN, Volume UP released, getevent failing, no answer), each guard checked by mutation. Device-checked on 2026-10-18: Volume DOWN prints "Cancelled: nothing was changed.", so getevent reads the volume keys when the manager runs action.sh. The 10 s timeout without an answer is not device-tested. The YES path (pm uninstall-system-updates) is not device-tested: the maintainer chose not to run it, because Android Auto must then be updated again with Aurora.
